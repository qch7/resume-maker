# Windows 隐私保护完整验收（2026-09-21）

## 范围和环境

在 Windows 上使用独立数据目录 `output/privacy-acceptance/data`、原生 Codex CLI 0.154.0、当前配置供应商的 GPT-6-Astra、真实 RapidOCR CPU 模型、浏览器和 Microsoft Word 完成验收。没有使用正式简历、个人证书或真实项目源码；没有重启或写入原 8765 实例。

真实调用保留完整应用路径：HTTP 接口 → 业务服务 → 本地提取/OCR → 隐私网关 → 原生 CLI → 模型。仅将供应商地址临时指向本机验收代理，代理先检查并记录完整 JSON 请求，再转发给原配置供应商；鉴权只在代理内存使用，不写入请求正文或抓包。代理不改变模型输入、模型回复和工具执行。

验收代理不是新增的生产保护功能。它保护本次测试，同时提供 CLI 实际外发内容的检查证据。

## 发现的问题和修复

| 问题 | 实际影响 | 修复及回归 |
| --- | --- | --- |
| 首次证书的学校、颁发单位标签未识别，换行值及 OCR 空白、全角格式漏检 | 原规则会将部分合成身份原文交给 CLI；验收代理在外发前拦截 | 增加中英文证书标签、下一行字段值、全角及格式控制符处理，已知身份匹配 OCR 间隔；保留原文还原 |
| CLI 内置模型目录覆盖工具开关 | GPT-6-Astra 使用另一套协议，未提供材料工具，出现额外工具声明；项目分析无法读取源码 | 每轮生成受控模型目录，保持所选模型名称，固定标准 Responses 协议，禁用 shell、补丁、代码编排及扩展工具 |
| Windows 短命令在加入 Job Object 前退出 | 并行证书和模板验收中偶发 `AssignProcessToJobObject` 拒绝访问 | 挂起创建、先加入 Job Object 再恢复主线程，启动失败回收进程及管道；增加延迟绑定的竞态测试 |
| Windows CRLF 写入副本时被再次转换 | 材料出现额外空行，引用行号偏移，证据降级为未核实 | 写入副本时保留原始换行；覆盖 LF、CRLF、CR，重新运行真实源码分析并核实引用 |

## 外发检查

合成标记覆盖中文姓名、带空格姓名、全角手机号、邮箱、隐藏身份证、住址、学校、颁发单位、证书编号、补充敏感词、未保存的模板姓名及源码凭据。检查同时展开嵌套 JSON、Unicode 转义和百分号编码，并归一化字宽、空白和格式控制符。

- 全程记录 32 次请求：6 次在修复前因身份漏检被验收代理阻断、1 次连接错误、24 次 HTTP 200、1 次主动取消引起的连接中断。
- 加强模型工具隔离后的 21 次请求：20 次 HTTP 200、1 次主动取消，合成身份原文及原始图片命中均为 **0**。
- 检查对象包括用户内容、模型上下文、输出 Schema、工具声明、工具参数和返回内容，超出应用“最近材料包”的范围。
- 这 21 次请求的工具声明均限于材料 MCP 及 CLI 的资源调度、交互工具；没有 shell、补丁、浏览器或代码编排工具。
- 返回的真实个人字段只在本机还原。源码凭据文件不进入材料，未知路径和凭据路径被工具拒绝。

## 结论边界

本轮覆盖的主要用户流程可用，修复后的测试个人信息被有效拦截，没有在检查到的实际模型请求中出现原文。回归测试未发现其他既有功能被本次改动破坏。

有限样本不能证明任意个人信息绝不会泄露。未知姓名、OCR 误认、间接身份线索和未覆盖编码仍可能漏检；受限工具也不是 Windows 内核隔离。生产系统尚无全量出站代理或新增静态加密，证书字段仍需人工核对。旧版本已经发送的数据不能撤回。
