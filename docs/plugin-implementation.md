# 插件化改造说明和验收

分支：`codex/plugin-architecture`。设计依据是 [完整方案](plugin-architecture-proposal.md)，插件作者使用 [当前 SDK](plugin-sdk.md)。参考 deepseek-harness 的实现思路，保留本地 Python + React 技术栈。

这次改造的结果是：**用户可以只安装制作简历需要的基础能力，再按需增加 AI、源码分析、模板、OCR、Word、荣誉库等能力。第三方可以开发插件，不必修改主应用的导航、服务总表或备份白名单。**

“系统插件必须有”指它们负责保存资料、保护隐私、管理任务和完成基本制作流程。隐私和 sandbox 都是系统插件，不会因为关闭 AI 或选择最小组合而被去掉。

## 1. 之前没做完的五件事，现在怎样处理

| 原来的缺口 | 本次落实后的行为 | 主要实现 |
| --- | --- | --- |
| 多实例、作用域和配置覆盖 | 一个插件可以创建多个独立实例，各有配置、资料和提供方；应用、工作区、任务分别管理寿命；能查看配置来源和恢复继承 | `runtime/instances.py`、`sdk/configuration.py`、`sdk/storage.py` |
| 公开扩展点和模块装配 | 来源、文档生成/导入/预览、日志展示、隐私补充规则、资料编辑器、命令和工作流均有实际入口；模型和模板分析可以附接或撤销 | `sdk/`、`plugins/`、`frontend/src/plugins/` |
| 业务模块互相读取私有实现 | 查询通过公共协议，跨模块删除通过同一事务中的持久引用规则；停用拥有者后仍保护引用；文档流程显式接收引擎，不自行加载 Word 或模板实现 | `sdk/services.py`、`storage.py`、`templates.py`、`plugins/ownership.json` |
| 附件分散、全量建表、重复成品 | 模板、证书、来源证据和历史成品统一使用资源服务；旧资料先备份、核验再迁移；新资料目录只建立所选模块的表；导出仅保存一份持久文件 | `infrastructure/assets.py`、`asset_migration.py`、`schema_resources.py` |
| 下载、安装、升级和故障恢复 | HTTPS 下载、摘要检查、实际进度、取消、版本锁、多个包一起检查；候选在副本和独立进程中试运行，正式切换由启动监督器完成，失败按资料兼容性处理 | `runtime/downloads.py`、`upgrades.py`、`environments.py`、`host_supervisor.py` |

业务服务的归属和跨插件私有导入由质量检查约束；公共类型、纯领域规则和底层算法继续保留分层。插件作者只依赖 SDK 和声明的能力，不应把仓库内部工具模块当作稳定 API。

## 2. 用户怎么选能力

默认 `standard` 有 41 个插件定义。`minimal` 有 18 个系统插件和 5 个必需的本地提供方，共 23 个。最小组合可以完成：

**手工项目 → 编辑经历 → 保存不可变版本 → 简历固定引用 → 填写资料 → DOCX 导出 → ZIP 备份 → 恢复后继续导出。**

最小组合不需要 AI、OCR、PDF 恢复或 Microsoft Word。Word 插件负责精确分页、PDF 和分页图片；普通 DOCX 制作由系统文档引擎完成。关闭荣誉库后仍能手工填写简历的荣誉栏目。

```sh
uv run resume-maker --profile minimal --data-dir ./output/manual-demo
uv run resume-maker --profile standard --data-dir ./output/standard-demo
```

日常通过顶部“插件管理”选择组合、增删实例、修改配置及提供方。先查看变更计划，再保存各窗口草稿并应用。依赖冲突会说明原因；不会把缺少能力的组合假装成已成功启用。`--profile` 是明确的启动覆盖，平时不传它就沿用当前资料目录的组合。

停用只停止能力；卸载移除安装记录；二者都保留资料。资料清理和资源回收是单独的明确操作。插件缺失时，普通编辑继续保留未知扩展字段，无法解释的导出内容要求明确的文字展示或隐藏标记。

## 3. 安装和更新怎么走

1. 填写本机 `.rmp` 路径，或填写发布者提供的 HTTPS 下载地址及 SHA-256。下载完还要检查包和确认代码信任。
2. 将一个或多个版本加入候选清单，选择是否启用。锁定的版本必须先解锁，才能换成其他摘要。
3. 系统一起检查依赖、配置、提供方和资料迁移。涉及迁移时，页面列出各插件的资料版本变化，并要求确认恢复方式。
4. 所有窗口先保存草稿，再等待请求、任务和资源实际结束。验证期间管理页面仍可查询进度和取消。
5. 生成完整备份，在资料副本中迁移，准备独立依赖环境，真正启动候选宿主并执行健康检查。正式资料和活动安装索引此时保持原样。
6. 候选通过后，监督器关闭旧宿主，提交整组环境和配置，再启动新宿主。健康观察通过后才开放业务操作，浏览器自动重新连接。

需要重启的配置修改和插件启停也使用同一套试运行流程。普通可排空的启停仍直接切换，不必每次重启。

下载进度是实际收到的字节数。安装和验证显示当前步骤，不编造百分比。取消验证会等待执行进程真正结束；开始请求或响应丢失后，可以用同一操作记录查询，不需要重新安装一遍。

## 4. 出问题时保护什么

- **候选检查失败：**原组合继续运行，资料不变。
- **正式迁移任一步失败：**整组副本不发布，正式库不留下前几个插件的半份改动。
- **新宿主启动失败、资料版本仍兼容：**自动恢复旧包、旧环境和旧配置，推进代次后重新启动，旧窗口不能覆盖新状态。
- **资料已迁移而新宿主失败：**保持维护状态，提供完整备份位置；不强行让旧代码写新资料，也不自动覆盖用户数据库。可以停机后用 `--restore` 明确恢复，故障目录会完整保留。
- **停电或进程中断：**下载、验证、迁移和切换都有持久记录；恢复时区分未发布、已切换、需人工恢复，不把“配置已写入”当作“新宿主健康”。
- **资料事务回滚：**引用、目录册、建表和业务写入一起撤销，缓存只在提交成功后失效。经历修订和历史成品仍不可变。

数据库现在是 **v8**。v6/v7 升级前留存原库。旧附件迁移核对文件集合及每个摘要，成功发布后才清理旧副本；中断后可从日志继续，不能重复复制或静默漏附件。恢复备份不会替未选择的模块新建业务表。

## 5. 隐私和 sandbox 各管什么

`sys.privacy` 负责内容：文字脱敏、图片保护、敏感值登记和本机还原。插件可贡献更严格的保护规则；缺包时，已登记的敏感资料仍受保护。模型提供方不能绕开统一出口。

`sys.sandbox` 负责执行授权，`sys.execution` 负责执行和真实进程回收。授权固定命令、环境、目录、材料摘要及代次。Windows 使用挂起启动和 Job Object 管理进程树。默认本地提供方不具备任意第三方代码的 OS 文件/网络强隔离；声明需要这些保证的任务会被拒绝。安装受信任 Host/worker 代码，仍意味着信任它具有当前账户权限。

## 7. 审查后的修正

`5a24c48` 的两项审查问题已复现并修正。停用失败后会重试仍持有资源的旧实例，再完整重建；如果清理仍失败，就保持维护、保留依赖和原持久配置，不再宣称恢复成功。自定义实例的 JS 和隔离页面按插件定义定位资源，RPC 继续按实例隔离。

SDK 的公开 Context 类型补齐配置、贡献、RPC 和生命周期，联合升级示例改用实际的 `packages` 字段。新增 [可复制的独立插件](examples/notes-plugin/README.md)，wheel 验收在仓库外构建它并通过真实 HTTP 检查安装、资源加载、停用和恢复。SDK 仍随草稿 PR 接受整体审查。

后续审查还修正了三个真实执行问题：消费者的停止屏障全部通过后才释放提供方资源；窗口必须等受影响命令实际结束并保存最终草稿后才确认切换，超时则保持未确认；包根目录的 `index.js` 可以作为可信客户端或隔离页面入口。测试覆盖停用、宿主关闭、消费环、命令超时重试和实际入口下载。
