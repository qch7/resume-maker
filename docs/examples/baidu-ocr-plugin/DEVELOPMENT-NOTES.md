# 独立插件开发反馈

本次只新增外部插件目录，不调整宿主 SDK、运行时、隐私流程或内置插件。以下记录当前实现中的实际约束，便于后续改进插件系统。

## 1. OCR 能力缺少公开的返回类型和完整契约

`sdk/model.py` 只有 `Provider.read_ocr(...) -> dict`；`ocr.backend` 的参数、分页、行坐标、置信度、异常和空结果要求没有独立 SDK 类型。插件作者必须阅读原引擎及业务消费者才能确认结构。

本插件自行实现并测试兼容字典。建议提供 `sdk/ocr.py`：`OCRBackend`、`OCRDocument`、`OCRPage`、`OCRBlock`、坐标单位、空结果语义、取消规则及可运行的合成契约验收器。

## 2. 凭据能力没有公开类型和持久配置入口

宿主有 `credentials` 能力，实际支持 `register/borrow/revoke`，但 SDK 未公开相应 Protocol，也没有第三方供应商通用的密码字段或凭据编辑控件。把密钥直接声明为普通 `config_schema` 字段会进入普通配置及客户端配置快照，不适合作为替代方案。

本插件依赖该能力，配置只保存外部凭据文件的路径，借用服务负责短期读取；凭据创建助手随源码交付。建议增加公开凭据类型、稳定持久引用及通用密钥编辑界面，插件只接收引用，不接触保存机制。该缺口使用户首次配置多出一个本机文件步骤。

## 3. 外部插件的身份保留规则不够显眼

安装器 `runtime/packages.py` 明确拒绝外部包使用 `sys.*` 或 `provider.*`。因此不能把第三方提供方直接命名为 `provider.baidu-ocr`，必须采用 `community.baidu-ocr` 等外部身份；服务名仍可为 `ocr.backend`。

这项隔离本身合理，建议在清单示例和安装规范明确列出保留前缀及“外部提供方身份”和“能力名称”的区别，并提供构建前校验。

## 4. 提供方切换需要同时操作两个开关

RapidOCR 将 `ocr.backend` 声明为 `one`，宿主求解器会在绑定前拒绝重复提供。因此“启用新引擎后选择使用它”不可行；先单独停用旧引擎也会让仍启用的 `ext.ocr` 缺少依赖。

本插件沿用同一份选择计划中的一停一启。建议设置页增加“替换当前提供方”操作，在候选计划中明确停用旧提供方、启用新提供方并展示影响。不要把装载顺序当作优先级；若需要多引擎并存，应单独设计集合和显式选择契约。

## 5. 依赖声明只检查，离线 Host 环境打包负担较大

插件只需 Pillow 和 PyMuPDF，清单声明这些依赖后安装器不会自动补装。`environment_lock` 可以准备环境，但 Host 锁必须包含 Resume Maker 及完整宿主依赖闭包，不能只附两个插件依赖 wheel。

本插件不提供不完整的环境锁，复用已有 OCR 环境；缺包时说明在宿主解释器停机安装。建议给插件作者提供官方锁生成和依赖环境构建工具，并在安装预览中给出可执行的依赖准备方案。不要把开发环境已有库当作最小安装环境也有。

## 6. 通用网络和请求取消能力缺少公共抽象

Host 插件自行执行 HTTP。没有 SDK 的连接池、绝对截止预算、按供应商限流或可取消 HTTP 服务；客户端 `context.request()` 也不接收 AbortSignal。RPC 清单超时不能替代 HTTP 请求实际终止。

本插件使用标准库、明确的单次等待和串行锁；停用信号在 HTTP 完成后核验，停止屏障等待实际执行结束。建议提供带截止和取消的网络服务，以及跨插件共享供应商配额的选用接口。已经送达供应商的请求仍不能由客户端保证撤回。

## 7. 公共资源边界和测试脚手架仍需进一步完善

现有 OCR 页数、字数、图像大小和复核门槛定义在 `integrations`，未作为公开 SDK OCR 契约导出。本插件为保持外部边界自行声明兼容的限制，宿主调整时需要双方同步。

独立笔记示例可以参考，但没有提供方替换示例或外部插件测试套件。安装、能力检查、启停和恢复验证只能自己组织真实宿主 HTTP 调用。

建议导出公开资源边界或能力协商，并提供无需导入 `tests.support` 的 `plugin-sdk validate/package/test` 工具。SDK 版本应反映公共契约变化；当前版本号不足以区分较早宿主是否具备所需插件功能。

## 保留的原系统行为

云端 OCR 的隐私状态及原有“本机提取”文案不属于本次修改范围。这里单独标明，避免把该后续任务和插件协议缺口混为一谈。实际账户鉴权、接口权限、额度和真实图片准确率由用户安装试用验证。
